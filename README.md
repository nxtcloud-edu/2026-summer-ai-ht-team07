## 트랙 1과의 연결 근거

트랙 1의 과제는 **"제조업·산업단지·중소기업의 생산성 및 안전 향상"** 이다.
YEDA가 이 트랙에 정확히 대응하는 이유는 세 가지다.

**1. 타겟이 실제로 중소·중견기업이다.**
반도체 후공정(OSAT)은 국내에 중소·중견기업이 다수 존재하는 영역이다. 전공정은 대기업 중심이지만
후공정은 그렇지 않다. 이들은 AI 인력이 부족해 자체 개발이 불가능하고, 그래서 외부 솔루션이 필요하다.
"AI가 필요하지만 스스로 만들 수 없는 중소기업"이라는 트랙 1의 문제 설정과 그대로 겹친다.

**2. 시장 공백이 실재한다.**
전공정 AI 수율 솔루션은 이미 대기업 시장을 중심으로 존재한다. 그러나 후공정, 특히 다이 픽업 공정에
대한 AI 최적화 시도는 거의 없다. 흔한 반도체 AI 프로젝트(웨이퍼 맵 결함 분류 등)와 겹치지 않는
영역을 선택한 이유이기도 하다.

**3. 개선 효과가 곧 수익이다.**
수율은 반도체 공정 수익성을 좌우하는 핵심 지표다. 다이 픽업은 정밀도가 높고 변수 간 비선형성이
커서 작은 조건 이탈이 큰 손실로 이어진다. 수율 1%p 개선이 그대로 생산성 향상으로 환산되는 구조다.

> 문제 정의는 **반도체 후공정 30년 이상 현직자 면담** 및 공개 논문·기업 자료를 근거로 했다.

## 문제 정의

### 다이 픽업 공정이란

웨이퍼를 절단해 만든 개별 칩(다이)을 다이싱 테이프에서 떼어내 다음 공정으로 옮기는 공정이다.
아래 세 가지가 동시에 맞아야 성공한다.

```
        [픽업 헤드 / 콜릿]  ← 진공으로 다이를 흡착
              ↓ 흡착
        ┌───────────┐
        │    다이     │        ← 얇을수록 크랙에 취약 (100~150 µm)
        └───────────┘
        ═══════════════       ← 다이싱 테이프 (UV 조사로 점착력 저하)
              ↑ 밀어올림
        [이젝터 핀]           ← 압력·속도·높이가 크랙을 좌우
```

1. **테이프 점착력이 충분히 낮아야** 한다 (UV 조사 시간·광량)
2. **이젝터 핀이 다이를 깨지 않고 들어올려야** 한다 (압력·속도·높이 × 다이 두께)
3. **픽업 헤드가 다이를 놓치지 않아야** 한다 (진공압)

이 조건들은 **서로 상호작용**한다. 예를 들어 얇은 다이에 핀을 빠르게 올리면 크랙이 나지만,
두꺼운 다이에서는 같은 속도가 문제되지 않는다. 변수 하나만 봐서는 원인을 찾을 수 없는 이유다.

### 현장의 문제

| 현재 | YEDA |
|---|---|
| 실패가 나면 숙련자 경험으로 조건을 조정 | 13개 변수 기반 성공률 예측 |
| "왜 실패했는지" 변수 단위 설명 불가 | SHAP으로 변수별 기여도 %p 분해 |
| 조건 탐색이 시행착오 | 학습 모델 기반 조건 탐색 및 제안 |
| 문제 인지가 늦음 | 임계값 초과 시 자동 알림 |

### 핵심 기능 4종

1. **수율(픽업 성공률) 예측** — 13개 공정 변수 → 성공 확률
2. **개별 다이 단위 실패 원인 분해** — SHAP 기여도 (확률 %p 단위)
3. **조정 가능 변수에 대한 최적화 가이드** — "무엇을 얼마로 → 몇 %p"
4. **임계값 초과 시 이메일 알림**

## 시스템 아키텍처 — 3-Tier

```
┌─────────────────┐       HTTP/JSON      ┌─────────────────────┐       SQL        ┌──────────────┐
│   Tier 1        │  ──────────────────▶  │      Tier 2         │  ─────────────▶  │   Tier 3     │
│   Frontend      │  ◀──────────────────  │      Backend API    │  ◀─────────────  │   Database   │
│                 │                       │                     │                  │              │
│   S3 Static     │                       │   EC2 :8000         │                  │   MySQL      │
│   HTML/JS/CSS   │                       │   FastAPI (Python)  │                  │              │
└─────────────────┘                       └─────────────────────┘                  └──────────────┘
```

| 항목 | 1-Tier (기존 Streamlit) | 3-Tier (현재) |
|---|---|---|
| 화면이 있는 곳 | EC2 (Streamlit) | **S3** |
| 로직이 도는 곳 | 같은 EC2 | **EC2 :8000 (FastAPI)** |
| 데이터 위치 | 서버 메모리 | **MySQL** |
| 서버 재시작 | 데이터 사라짐 | **유지됨** |
| 서버가 멈추면 | 화면도 안 뜸 | **화면은 뜸** |
| DB 비밀번호 | 해당 없음 | **EC2 안에만** |

### API 엔드포인트

### 설계상 중요한 경계

**1. 생성 규칙과 최적화 가이드의 방화벽**

`optimize/`와 `explain/`은 `data/physics.py`를 import하지 않는다.
생성기의 임계값을 정답으로 재사용하면 순환 논리가 된다.
이 규칙은 `tests/test_contracts.py::test_no_generator_leak`이 강제한다.

**2. 조정 가능 / 불가능 변수의 분리**

`die_thickness`(제품), `tape_type`(자재), `runtime_hours`·`vacuum_status`(설비 상태)는
최적화 탐색 공간에서 구조적으로 제외된다 (`schema.ADJUSTABLE`).

**3. Mock 폴백**

모델 파일이 없어도 API 서버가 mock 모드로 정상 동작한다. 데모가 멈추는 일이 없다.

### 설계상 중요한 두 가지 경계

## 데이터 출처 — 합성 데이터 명시

> ### ⚠️ 본 프로젝트는 **합성(synthetic) 데이터**로 학습되었습니다.
> 실제 기업의 공정 데이터가 아닙니다.

### 방법론

반도체 후공정의 실공정 데이터는 **기밀 이슈로 외부 접근이 불가능**하다.
따라서 다음 절차로 합성 데이터셋을 설계했다.

1. **변수와 범위** — 공개 논문·설비 사양서·기업 공개 자료에서 다이 픽업 공정의 주요 변수 13개와
   각각의 정상 운전 범위를 수집했다.
2. **물리 관계** — 반도체 후공정 30년 이상 현직자 면담을 통해 각 변수가 픽업 성공률에 미치는
   **방향과 상대적 크기**, 그리고 변수 간 상호작용을 정의했다.
   근거는 변수 단위로 [`docs/PHYSICS_RATIONALE.md`](docs/PHYSICS_RATIONALE.md) 에 기록되어 있다.
3. **확률적 라벨 생성** — 조건 이탈 정도를 연속적으로 반영한 잠재 점수를 만들고,
   로지스틱 변환 후 **베르누이 샘플링**으로 라벨을 뽑았다. 동일 조건에서도 결과가 갈린다.
4. **계측 현실성** — 라벨 생성 후 관측값에 센서 분해능 수준의 노이즈를 입히고 반올림했으며,
   1~3% 수준의 결측을 삽입했다.
5. **검증** — 홀드아웃 분리로 평가했고, 어떤 단일 임계값 규칙으로도 타겟이 재현되지 않음을
   자동 테스트로 확인한다 (`tests/test_generator.py`).

### 우리가 무엇을 고쳤는가 (초기 프로토타입의 결함)

초기 프로토타입 데이터(`yeda_simulated_data.xlsx`, 5,000행)에는 치명적 결함이 있었고,
**이번 리포지토리의 1순위 과업이 그 교체였다.**

| | 초기 프로토타입 | 현재 |
|---|---|---|
| 라벨 생성 | 4개 부등식의 **결정론적 AND** | 잠재 점수 → 로지스틱 → 베르누이 샘플링 |
| 재현율 | 5,000행 **전부** 규칙과 일치 (오분류 0건) | 단일 규칙으로 재현 불가 (테스트로 강제) |
| 변수 기여 | 13개 중 9개가 타겟 상관계수 −0.03~0.01 (순수 난수) | 13개 전부 기여, 크기 차등 |
| 상호작용 | 없음 | 3개 (부호 교차형 포함) |
| 정확도 | RF 99.86% / 단일 트리 99.84% | **80% 초중반** |
| 최적화 가이드 | 하드코딩한 규칙을 되읽는 **순환 논리** | 학습 모델에서만 유도 (테스트로 강제) |

초기 데이터의 문제는 모델이 공정 물리가 아니라 부등식 4개를 학습했다는 점이며,
**pandas 세 줄로 검증 가능한 수준의 결함**이었다. 현재 생성기는 다음을 만족한다.

- 성공률 65~80% (클래스 균형)
- 베이즈 정확도 상한 0.82~0.90 — **완벽한 모델조차 100%를 낼 수 없다.**
  라벨이 확률적이기 때문이며, 학습 정확도가 이 값을 크게 넘으면 누수를 의심한다.
- 시드 고정, 생성 파라미터 전체를 `configs/data_gen.yaml` 로 외부화

### 외부 데이터

**UCI SECOM** (1,567행 × 590특성, 불량률 약 6.6%) — 실측 반도체 팹 센서 데이터.
전처리→학습→평가 파이프라인이 실측 데이터에서도 동작함을 보이는 **일반화 검증** 용도로만 사용한다.

> ⚠️ SECOM은 변수가 익명 센서값이라 물리적 의미를 알 수 없다.
> 따라서 **최적화 가이드는 적용하지 않는다.** 이 파트는 파이프라인 검증으로만 포지셔닝한다.

## 모델 성능

**평가 원칙**: accuracy 단독 보고를 하지 않는다. 성공률이 약 70%이므로 "전부 성공"이라고만 찍어도
정확도 70%가 나온다. **PR-AUC · recall · macro-F1** 을 함께 본다.
또한 확률을 수율(%)로 화면에 표시하므로 **신뢰도 곡선(calibration)** 을 반드시 포함한다.

### 홀드아웃 성능 (20%, 시드 고정)

<!-- 출처: artifacts/metrics/model_comparison.csv — 발표 슬라이드의 숫자도 반드시 이 파일에서 가져온다. -->

| 모델 | Accuracy | PR-AUC | Recall | macro-F1 | Brier↓ | ECE↓ |
|---|---|---|---|---|---|---|
| LogisticRegression (베이스라인) | 0.809 | 0.902 | 0.890 | 0.775 | 0.134 | 0.031 |
| RandomForest | 0.832 | 0.933 | 0.923 | 0.797 | 0.123 | 0.043 |
| LightGBM | 0.849 | 0.941 | 0.923 | 0.821 | 0.113 | 0.043 |
| **LightGBM + 단조 제약** ★ | **0.854** | **0.944** | **0.933** | **0.825** | **0.109** | **0.027** |

> 데이터 생성 조건: 8,000행, 시드 20260810, 성공률 66.8%, 베이즈 정확도 0.872, 결측률 1.8%.
> 단조 제약 모델이 제약 없는 LightGBM 대비 accuracy +0.5%p, ECE가 절반 수준으로 개선되었다.

> 교차검증(5-fold OOF) 결과도 유사: 본선 모델 OOF PR-AUC 0.945, OOF accuracy 0.829.
> 홀드아웃과 OOF 사이에 큰 차이가 없어 과적합 우려가 낮다.

### 왜 LightGBM + 단조 제약인가

**1. 선형 모델로는 부족하다.** 공정 변수에는 내부 최적점이 있는 관계(핀 높이·온도)와
변수 간 상호작용(핀 속도 × 다이 두께)이 존재한다. LogisticRegression 베이스라인과의 성능 차이가
이 구조의 존재를 보여준다.

**2. 딥러닝은 쓰지 않는다.** 8,000행 정형 데이터에서 트리 앙상블 대비 이점이 없고,
"왜 이 구조인가"를 방어하기 어렵다. AutoML도 같은 이유로 배제했다.

**3. 단조 제약이 이 프로젝트의 핵심이다.**
LightGBM의 `monotone_constraints` 로 **물리적으로 방향이 확정된 8개 변수**에 제약을 걸었다.

```
현직자 면담으로 확인한 공정 물리 법칙  →  모델 제약으로 주입
```

| 변수 | 제약 | 물리적 근거 |
|---|---|---|
| `uv_time`, `uv_intensity` | +1 | UV 조사 → 점착제 경화 → 이형 용이 |
| `pin_speed` | −1 | 빠를수록 굽힘 응력 ↑ → 크랙 |
| `pin_pressure` | +1 | 박리 구동력 ↑ |
| `head_vacuum`, `pin_vacuum`, `vacuum_status` | −1 | **음수 게이지압**: 값이 작을수록(더 음수) 진공이 강함 |
| `humidity` | −1 | 계면 수분 → 미세 슬립 |
| `runtime_hours` | −1 | 콜릿 마모 누적 |
| `die_thickness` | +1 | 굽힘 강성 ↑ → 크랙 저항 |
| `pin_height`, `temperature` | 0 | **내부 최적점 존재** → 제약 없음 |

제약이 주는 것은 성능만이 아니다. 데이터에 우연히 섞인 노이즈 때문에 모델이
"진공을 약하게 하면 성공률이 오른다" 같은 **물리적으로 불가능한 조언**을 내놓는 것을 구조적으로 막는다.
최적화 가이드가 현장에서 신뢰받으려면 이것이 필요하다.

## 개발 규칙

### 브랜치 전략

24시간짜리 일정에서 복잡한 브랜치 전략은 그 자체가 리스크다. 최소한만 쓴다.

```
main                    항상 데모가 돌아가는 상태로 유지. 직접 푸시 금지.
 └─ feat/<파트>-<담당>   각자 작업 브랜치
     예: feat/data-C, feat/explain-D, feat/ui-E, docs/physics-A
```

- **작업 단위로 자주 머지한다.** 하루 종일 브랜치를 안 합치면 M3에서 통합이 터진다.
- 머지 전 `make test` 통과를 확인한다.
- `src/yeda/schema.py` 변경은 **E가 머지하고 전원에게 공지**한다.
- 충돌이 나면 혼자 풀지 말고 파일 소유자와 함께 푼다 ([`ROLES.md`](ROLES.md) 소유권 표).

### 커밋 컨벤션

```
<타입>(<범위>): <한 줄 요약>

타입:  feat  기능 추가        fix   버그 수정
       data  생성기·데이터     model 학습·평가
       docs  문서             test  테스트
       chore 설정·빌드

예시:
  feat(optimize): 조정 불가 변수를 탐색 공간에서 제외
  data(generator): 핀 속도 × 다이 두께 상호작용 추가
  fix(ui): 모델 없을 때 mock 모드로 폴백하도록 수정
  docs(physics): 진공압 부호 규약 근거 보강
```

### 코드 규칙

1. **파일 소유권을 지킨다.** 자기 소유가 아닌 파일은 고치지 않는다.
2. **파라미터는 `configs/` 로 뺀다.** 코드에 상수를 박지 않는다.
3. **`src/yeda/schema.py` 가 유일한 진실 원천이다.** 컬럼명·범위를 다른 곳에 복사하지 않는다.
4. **`data/physics.py` 를 모델·설명·최적화에서 import 하지 않는다.** (테스트가 강제)
5. **노트북에 프로덕션 로직을 두지 않는다.**
6. **데모를 멈추는 예외를 만들지 않는다.** 실패는 흡수하고 화면에 표시한다.
